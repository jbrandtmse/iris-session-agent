## What Went Well

1. **Manual-testing-as-empirical-battery worked.** The user's *"don't wait for retro, investigate any error or malbehavior"* direction (recorded mid-Epic-3) flipped the Epic 1 + 2 pattern: instead of the user-led empirical battery surfacing N bugs at retro time, the lead-led empirical battery surfaced + fixed 5 bugs in-cycle. The retro now opens with fixes already shipped, not bugs to triage. **First epic where Rule 6's spirit was achieved — battery happened, in-cycle, before retro proposal.**

2. **Asset-class pivot eliminated two deferred items in one move.** Story 3.6's lead-driven smoke surfaced two integration bugs at once (`${cspdir}` ZPM template not expanded + Web Gateway in-process Path cache requires reload). Both were initially deferred to Story 3.7 (per Rule 9). Then Perplexity research + a one-question pivot to a `%CSP.Page` subclass streaming the asset from IPM module Root made BOTH bugs structurally impossible — no static directory, no CSP application Path, no gateway cache. **One architectural change closed two deferred items + simplified the install footprint.** [`src/SessionAgent/UI/ChatPanelAsset.cls`](../../src/SessionAgent/UI/ChatPanelAsset.cls).

3. **Three Rule 9 binding closures verified end-to-end.** This was the first epic where the "predicted-bug deferral" pattern proved its value. Story 3.2 reviewer predicted the consumer-side `data-tool-call-id` lookup gap → reassigned to Story 3.4 → Story 3.4 spec author grepped, picked Path 2, shipped tool-name lookup with dispatch-index fallback → bug never shipped. Same shape for Story 3.3 F5 → Story 3.5; same shape for Story 3.7 → Story 3.8. **Rule 9 works when the next-story spec author actually greps. Three for three this epic.**

4. **Mid-epic scope expansion via /bmad-correct-course was clean.** Sprint Change Proposal added Stories 3.8 + 3.9 + Epic 6 Story 6.4 with explicit triage rationale per item. The proposal was approved with a single user *"yes"*; the artifact-edits landed in commit `d350d3f`; the new stories landed within the same epic cycle. **The correct-course mechanism didn't add ceremony — it added a gate where one was needed.**

5. **Sample interop production lifted the "no rich data" objection.** Story 3.9 was added in the correct-course pass specifically because Story 3.7's walkthrough on the bare HSCUSTOM namespace (sessions 1–N from prior unit-test runs) wasn't compelling enough — operators want to see the chat panel against real-shaped data. Story 3.9 ships an installable order-flow production with 4 error scenarios; subsequent re-walkthroughs against sessions 357, 371, 372, 374, 376, 396, 397 produced richer agent answers, validated citation-chip click navigation, and exposed the cross-session disclosure unreliability that Story 3.8 then closed. **The sample production was both the demo data AND the empirical-test fixture.**

6. **Capability-hallucination root cause was ObjectScript-side, not LLM-side.** When the agent confidently claimed it could *"search by message body content"* (a Story 4.6 / Epic 8 capability), the natural first instinct was prompt-engineering. But the root cause was [`AgentDefaults.GetSystemPrompt`](../../src/SessionAgent/Config/AgentDefaults.cls) hardcoding all 13 planned tool names. Removing the enumeration in favor of *"use only the tools in that list, do not invent tool names or describe capabilities you don't actually have"* fixed it deterministically. **The fix is a one-line directive that scales as new tools land — Epic 4 / 8 / 10 won't need to revise the prompt as their tools come online.**

7. **Audit ledger held under load.** 200+ LlmCall + 130+ ToolCall rows accumulated across the epic's manual testing without a single integrity gap. The Epic 2 NFR-S4 guarantee continues to hold under richer real-world flows than the Story 2.12 SmokeTest exercised.

8. **All 10 stories committed clean — zero rollbacks, zero amends.** The dev → code-review → commit pipeline didn't require a single story re-cycle. Stories 3.7 → 3.8 → 3.9 → fix-now bundles all landed in linear order without revisiting prior commits.

## What Didn't Go As Well

1. **Capability hallucination shipped through 9 stories before being caught.** [`AgentDefaults.GetSystemPrompt`](../../src/SessionAgent/Config/AgentDefaults.cls) hardcoded 13 tool names since Story 2.4. Story 2.11 only loaded 3 of them (`session_summary`, `session_timeline`, `message_headers`). For 9 stories — Stories 2.4, 2.10, 2.11, 2.12, 3.0, 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7 — the agent described capabilities it didn't have. **Code review didn't catch it. Tests didn't catch it (the unit test asserted the tool names WERE present in the prompt — exactly the wrong invariant).** It was only caught when a manual-test session asked the agent what it could do and got back an answer naming `find_sessions_by_body`. The unit test's invariant has now been inverted to a *negative* assertion.

2. **UTF-8 mojibake shipped in the welcome message.** The `Â·` character in the chat panel introduction was visible to anyone who opened the panel for the first time — and went unnoticed through 6 stories (3.2, 3.3, 3.4, 3.5, 3.6, 3.7) before the user asked *"There are funny characters in the introduction message of the agent. Those need to be fixed."* Default `%Stream.FileCharacter` reads bytes as Latin-1; UTF-8 multi-byte sequences come through as garbage. **One-line fix (`tStream.TranslateTable = "UTF8"`) but a high-visibility miss.** The deeper systemic cause: no story explicitly tested the rendered text content — the smoke runbook checked DOM structure, accessibility tree, network requests, and console errors but not "are the actual user-visible characters readable English." Worth a Rule 12 candidate.

3. **Cross-session notice persistence asymmetry only surfaced at reload time.** Story 3.8 dev verified the live response carried the notice. Story 3.8 reviewer verified the live response carried the notice. The persistence path (where `tTurns` was populated BEFORE the prepend block runs) wasn't exercised until manual reload. **The unit test fixture for Story 3.8 captured the live response shape but didn't reload from `Chat.History.TurnsJson` and re-render.** Same pattern as #2 above — the test exercised one slice of the contract, not the full operator journey.

4. **Story 3.7's walkthrough revealed the visual differentiation gap that should have been caught at Story 3.1 (CSS) or Story 3.2 (renderer).** All-identical message styling for operator + agent + error turns made the chat hard to scan. The fix landed in Story 3.7 itself (You — / Agent — prefixes + bg tint differentiation via existing tokens) — but the gap shape (operator vs. agent attribution per UX-design-spec line 776) was specified, never implemented, and never reviewed. **The story-spec-to-code traceability missed this because UX-design-spec line 776 wasn't cited in Stories 3.1 or 3.2's Dev Notes.** Worth tightening: when a story implements a specified UX detail, the spec line should be the citation, and the code review checklist should re-read the specified line and verify the rendered output matches.

5. **Manual testing required user-driven kickoff.** The lead's natural inclination after Story 3.7's commit was *"propose the retrospective."* The user's *"Actually, we want to do a round of manual testing first. We should create data in the sample solution and then interact with it using the Chrome-DevTools MCP."* re-routed to manual testing → which then surfaced the 5 bugs that landed in commits `ebde251`, `768be17`, `d7ebf80`. **Rule 6 (sharpened) requires the empirical battery before the retro proposal — but it doesn't require the lead to drive a full lead-led walkthrough as the empirical battery.** Story 3.7's "lead-driven walkthrough" was treated as the battery; the user's redirect proved that wasn't enough. Worth tightening Rule 6 further: the empirical battery must include a session-shaped flow against rich data (sample production or equivalent), not just an internal smoke.

6. **Some stories ran long.** Story 3.9 spec was 251 lines — one over the Rule 1 250-line cap. The over-shoot was due to the 4-scenario error-mode table (legitimately load-bearing) but it's a sign the cap is being approached. **Worth flagging as a Rule 1 watch-item rather than relaxing the cap.**
