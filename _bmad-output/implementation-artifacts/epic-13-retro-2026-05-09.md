## What Went Well

**1. Bottom-up execution ordering paid off.** `get_queue_state` (simplest, ~40 LOC, global-based) shipped first and validated the entire "add a new tool" path — story file format, ISV test bump pattern, registry registration, compile cycle — before the more complex stories touched it. Every subsequent story inherited a working template. Zero "this is the first one, let's figure it out" friction.

**2. AI-1 + AI-2 carry-forwards were immediately load-bearing.** The SQL injection 4-layer defense rule was referenced in Story 13.5's AC-2 contract the same day the rule was added. `RegressionSweepCount()` was called by every dev agent in Stories 13.2–13.5 without any of them constructing the canonical numerical-MAX SQL probe from scratch. Both carry-forwards from Epic 12 delivered exactly the ROI they were designed for.

**3. Reviewer-as-net caught every MEDIUM.** All 3 MEDIUMs were caught and auto-fixed by reviewers in the same commit — none shipped. The EXPECTEDTOOLCOUNT miss (cr-13-4) and the non-canonical error envelope (cr-13-5) were both systematic gaps the dev agents hadn't internalized; the reviewer layer absorbed them cleanly.

**4. BoundedWhereInvariantTest auto-discovery worked end-to-end.** Story 13.5's `GetIndexedLeadColumns()` declaration was picked up by `BoundedWhereInvariantTest` automatically (6/6 pass) — no manual test registration, no suite modification. The FR59 cross-matrix gate continues to scale by convention rather than configuration.

**5. Task 0 pre-flight probes prevented spec-based wrong assumptions from reaching dev.** The `tool-catalog-expansion-2026-05-09.md` source had stale Ens.Config.Item API assumptions (`NameKeyOpen()`, `NameOpen()` — neither exists; `Ens_Config.Setting` as SQL table — doesn't exist). Task 0 caught both before Story 13.3 was handed to the dev agent. Corrected API documented in Dev Notes; dev implementation was correct on first attempt.

## What Didn't Go Well

**1. `%EXACT()` in SELECT column list silently breaks `%Get("colName")`.** Story 13.3 dev used `SELECT %EXACT(ID), %EXACT(ClassName), ...` and then called `tRS.%Get("ID")` — which returned `""` because `%EXACT(ID)` renames the column. Required switching to positional `%GetData(1)`, `%GetData(2)`, etc. This is the kind of IRIS SQL quirk that should be codified so future devs don't re-discover it. **→ New AI-1 below.**

**2. Story 11.2's `EnsureIsErrorOnPrepareFailure` sweep didn't fully propagate to new-tool muscle memory.** The sweep patched 33 existing call sites in Epic 11. Story 13.5's dev still wrote a raw `{"isError":1, ...}` envelope for the prepare failure path — exactly the pre-sweep pattern. The reviewer caught it (MEDIUM auto-fixed), but the intent of a sweep story is to prevent re-introduction. **→ New AI-2 below.**

**3. `InspectionSuiteVerificationTest.EXPECTEDTOOLCOUNT` bump missed by two devs (13.2, 13.4).** Both stories shipped the tool correctly registered, but didn't bump the count. Both were caught by reviewers as MEDIUM auto-fixes. The ISV test exists precisely to catch count drift — it worked — but two misses in five stories suggests the spec template for Inspection tools needs to make the bump more prominent. **→ New AI-3 below.**

## Patterns Observed Across Stories

**Pattern A — Spec source quality determines Task 0 scope.** Stories 13.1, 13.2, 13.4 had correct API assumptions in the source doc; Task 0 was confirmatory. Story 13.3 had two wrong API assumptions; Task 0 was corrective. The pre-flight probe's value is asymmetric — when it catches a wrong assumption it saves the entire dev cycle; when it confirms a right one it's a few minutes well spent. Never skip.

**Pattern B — Serial object collections have no SQL table.** `Ens.Config.Setting` is a `%SerialObject` embedded in `Ens.Config.Item`'s data node. No SQL table exists; the only access is `tItem.Settings.GetNext(.tKey)` iteration. This pattern also applies to `Ens.Config.ModifiedSettings` and any other embedded serial collections. Worth noting for future stories touching `Ens.Config.*`.

**Pattern C — Search tool vs. Inspection tool distinction held.** `find_sessions_using_class` correctly extends `SessionAgent.Tool.Search.Base` (not `Tool.Inspection.Base`), lives under `src/SessionAgent/Tool/Search/`, and auto-registers with the `message-search` agent context. The architectural separation between Inspection (single-session, %OpenId-based) and Search (cross-session, SQL-bounded-WHERE) was respected throughout.
