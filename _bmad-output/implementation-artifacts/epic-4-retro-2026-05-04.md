## What Didn't Go As Well

1. **Reviewer-caught bugs outweighed dev-caught bugs.** 5 dev-shipped bugs that the reviewer found and either fixed or surfaced for fix-now. In an ideal pipeline the dev would catch most of these via empirical self-verification before passing to review. The pattern across the 5 catches:
   - Description-text drift after Task 0 fix-nows (Story 4.4 x2): dev redesigned the implementation but didn't audit the class Description text against the new behavior.
   - Silent `%Prepare` failure swallow (Story 4.3): Try/Catch shape was stylistically correct but didn't propagate the prepare failure as `isError:1` envelope.
   - `FormatExceptionForOperator` off-by-one (Story 4.7): dev wrote helper but didn't capture verbatim input/output proof in Completion Notes.
   - Wider Story 4.5 R-1 sweep needed (Story 4.7): dev addressed the named carry-forward (1 tool) but didn't sweep the full pattern across all 12 tools.

   Common thread: dev is claiming completion based on tests-passing without empirical proof of the AC's actual contract. Action Item AI-2 sharpens Rule 2 to require this.

2. **MCP truncation masked a real test failure in Story 4.7.** Story 4.7 dev's Completion Notes claimed "all 8 methods Status=1" — but `InspectionSuiteVerificationTest` has **10 methods**, and **9 of 10 passed**. The 10th (`TestFormatExceptionForOperatorStripsNoise`) was failing because of the `FormatExceptionForOperator` off-by-one. The MCP `iris_execute_tests` envelope showed a green-looking response that masked the failing method. Reviewer caught it via direct `%UnitTest_Result.TestMethod` SQL probe. Without that habit, a real bug would have shipped clean. **Action Item AI-1 codifies the SQL-probe-as-ground-truth invariant.**

3. **Sample production state required re-Bootstrap on multiple stories.** Stories 4.3, 4.6, 4.7 all needed `do ##class(SessionAgent.Sample.Bootstrap).Install()` + `Production.Start()` before their AC-8 verification batteries because the sample production was UNINSTALLED at story start. Process-improvement opportunity: Sample production should be re-Bootstrapped at Epic-cycle start (Step 1 sprint planning), not per-story. Worth a one-line addition to the operator-state checklist (Rule 7 application).

4. **Welcome message under-statement was a Rule 12 / Rule 4 gap.** The chat-panel `renderWelcomeMessage` text claimed only the 3 Epic 3 inspection tools despite Epic 4 shipping 10 more. This is exactly the failure shape Rule 12 (rendered-text readability) is designed to catch — but Rule 12 was applied per-story to NEW UI work, not to PRE-EXISTING welcome text after the tool catalog grew. Stale-reference scan (Rule 4) doesn't currently include "operator-facing static text vs. shipped capability" as a check target. Caught by user-led manual-test pass — exactly the empirical-battery surface that's supposed to catch it. **No new rule needed; Rule 12 + Rule 6 sharpened working as intended; the gap was that Rule 12 wasn't applied to the welcome string this cycle because no story explicitly touched it.**

5. **Pre-existing IRIS log mojibake in `Ens.Util.Log` SessionId=0 row.** Surfaced during manual-test sample-prod SQL probes: `"خطأ <Ens>ErrInvalidProduction: Invalid Production"` — Arabic-script characters where ASCII "ERROR" should be. NOT from Epic 4 code; appears to be a legacy IRIS-side row from older sessions. Out of Epic 4 scope but worth documenting — operators querying event-log on this dev install will see this text. Document-only; no code change.

6. **`<Ens>ErrGeneral` is unmatched in the curated `explain_error` table.** Surfaced during manual-test session 2114 walkthrough — `<Ens>ErrGeneral` is one of the most common Ens-runtime errors (used for injected sample failures, generic Ensemble errors, etc.) but the Story 4.7 curated 10-entry table doesn't include it. Story 4.7 dev returned the honest "unmatched" envelope. Worth adding `<Ens>ErrGeneral` + a small set of common Ens-specific codes (`<Ens>ErrBPTimeout`, `<Ens>ErrNoTimeout`, etc.) to the table in a future story or via opportunistic carry-forward.

## Significant Discoveries (epic-update potential)

**One.** **MCP `iris_execute_tests` truncation can mask FAILING test methods, not just count discrepancies.** Story 4.0 AC-4 codified the count-truncation workaround. Story 4.7 surfaced the deeper failure mode: when a test method status=0 lands in the truncated tail, the MCP envelope may not surface it, and a green-looking response masks a real failure. **Implication for Epic 5+: the SQL-probe-against-`%UnitTest_Result.TestMethod` invariant is binding — the global is ground truth.** Codified in AI-1.

**Two.** **The dev → review pipeline separation is high-value when reviewer empirically probes the AC contract.** Five distinct reviewer catches in Epic 4 — all involved the reviewer running an empirical probe (SQL, method invocation, class introspection) that the dev didn't run. The catch rate suggests the dev's empirical-self-verification is currently under-disciplined. **Implication for Epic 5+: AI-2 sharpens Rule 2 to require empirical proof of the AC contract in dev Completion Notes — shifts the catch from review to dev.**

**Three.** **First successful cross-codebase Task 0 binding handoff to Epic 8.** Story 4.6's "Task 0 probe captures (binding for Epic 8 Story 8.5)" heading is the first cross-codebase carry-forward in this project. Pattern is durable: when a story is the first cross-codebase consumer of an external surface, capturing Task 0 findings under a verbatim/greppable heading lets the next consumer cite the prior findings instead of re-probing. **Per the lead's Lane 3 call: this is sufficiently covered by existing Rule 9 grep practice; no new rule needed.** The `binding for Epic N Story M.x` heading convention IS the mechanism.

**Four (concern).** **Sample production state UNINSTALLED at multiple per-story start points.** Stories 4.3, 4.6, 4.7 all required mid-story re-Bootstrap. Process improvement opportunity: re-Bootstrap at Epic-cycle Step 1, not per-story. Codified in AI-3 (Rule 7 watch-item) — Story 5.0 will add to operator-state checklist.
