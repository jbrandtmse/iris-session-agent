## Headline Findings

### What went well

**1. Bug-report-as-spec source pattern.** Every Story 12.x spec cited the walkthrough bug report (`walkthrough-bugs-2026-05-08.md`) as its source-of-truth. Each bug entry already had reproduction + verified root cause + recommended fix shape. Dev agents inherited that analysis directly — no spec-time investigation drift, no rediscovery cost. This was the highest-leverage move of the cycle: front-loading the investigation into the bug-collection phase paid off across 8 stories.

**2. Walkthrough → Sprint Change Proposal → Epic 12 governance loop worked end-to-end.** The user-driven walkthrough surfaced 11 findings in a single session. The Sprint Change Proposal converted them into an 8-story plan with bundling rationale. The `/epic-cycle 12` pipeline drove all 8 stories through to completion with NO scope creep, NO missed findings, NO mid-cycle replanning. The governance pattern is reusable for any future "walkthrough-driven epic".

**3. Per-story chrome-devtools-mcp evidence consistently captured.** Every UI-touching story (12.1, 12.4, 12.5, 12.6) saved a screenshot to `_bmad-output/implementation-artifacts/12-X-screenshot-...png`. By the time Story 12.7 needed README screenshots, the artifacts were already on disk — Story 12.7's "Task 3" was literally `cp` + rename. Zero wasted effort.

**4. Reviewer-as-net pattern paid off twice.** Story 12.5 reviewer (`cr-12-5`) caught two MEDIUM gaps the dev had missed: (a) the existing Reset Ribbon button didn't clear the new agent-filter property (operator-visible inconsistency), (b) `CreateResultSet` failure paths silently leaked unfiltered results while the badge still claimed filter active. Both auto-fixed in the same commit per Rule 8. Without the reviewer, both would have shipped as latent bugs.

**5. Bundle architecture validated by reviews.** The 8-story split bundling decisions (BUG-01 + BUG-08 → Story 12.1; BUG-02 + BUG-03 → Story 12.2; ENH-09 + ENH-10 + ENH-11 → Story 12.7) all reviewed cleanly without "should have been split" feedback. Bundling the small-and-similar items reduced 11 findings → 8 stories without sacrificing reviewer partition (different files within each bundle).

**6. Story 12.0 documentation-only audit trail surfaced a real drift.** Dev-12-0's clarification ("the triage table covers 9 items but Epic 10 retro contains 5 AIs not represented") was a legitimate catch the lead missed during initial drafting. Spec-time review caught a documentation drift that would have otherwise propagated into an incomplete audit trail. Validates the value of running the dev pipeline even on documentation-only stories.

### What didn't go well

**1. Pre-retro empirical-battery checklist emitted late.** Per Rule 6 sharpened, the lead must emit the 5-bullet checklist BEFORE proposing the retrospective question. The lead asked "Would you like to run a retrospective?" via `AskUserQuestion` and only emitted the checklist AFTER the user answered yes — a Rule 6 sequencing violation. Recovery was clean (checklist emitted before invoking the skill), but the rule's "transcript precondition" wording was bypassed in the moment.

**2. Story 12.0 retro-AI coverage drift.** The lead's initial Triage Decisions table (9 items) missed 4 Epic 10 retro Action Items (AI-1 through AI-4 — all rule-codification work that was originally bound to never-created Story 11.0). Dev-12-0's clarification surfaced the gap. Root cause: the lead read `epic-10-retro-2026-05-08.md` for "deferred items" but didn't enumerate Action Items by AI-N. Once expanded, 5 new rows landed (4 retro AIs DEFERRED to v2 + 1 RESOLVED-by-Story-11.1 — the Story 10.13 MaxTokens cascade overwrite, closed two epics earlier than the original deferral assumed).

**3. Substring grep gotcha repeated.** Story 12.3's spec called out the substring containment gotcha (`SessionAgent.EnsPortal.VisualTrace.zen` contains `EnsPortal.VisualTrace.zen` as a substring). The dev correctly used the strip-and-grep pattern in the unit test. But if a future maintainer adds a SECOND custom URL reference and reverts one of them to the bare standard URL, the existing test wouldn't catch it (per the cr-12-3 reviewer's analysis). Reviewer noted no predicted-bug shape today, so deferred as cosmetic — but the test pattern is fragile in principle.

**4. Per-story `iris_execute_tests` MCP truncation handling re-discovered each story.** Stories 12.1, 12.3, 12.4 each had a moment where the MCP envelope returned `total:0` (when `level: "method"`) or truncated rows (when running across many classes). Each dev agent re-discovered the canonical numerical-MAX SQL probe workaround per `.claude/rules/object-script-testing.md`. The rule is documented; agents read it; but the discovery still cost a round-trip per story. Possible improvement: bake the probe into a helper class method (e.g., `Test.Util.RegressionSweepCount()`) so dev agents don't need to construct the SQL each time.

**5. Story 12.5 SQL injection 4-layer defense verbose.** The dev correctly implemented 4 validation layers (JS render-time, JS click-time, ClientMethod re-validate, ObjectScript $Match re-validate). Reviewer verified all 4 present. But this is now a project pattern — should be codified as a project rule for future Zen ZenMethods that accept agent-derived data. **Action item below.**

**6. Story 12.6 dev's mid-flight workaround.** Dev-12-6 hit an operator-credential-resolution wall (the AgentConfig form's `credCombo` Zen widget didn't propagate JS-set values into the underlying control state on Save). Dev worked around by direct-injecting a search-shape `Chat.History` fixture via a temporary `Story126Walkthrough.cls` helper, deleted after the walkthrough. This worked, but the underlying form-quirk is real and unrelated to Story 12.6's BUG-07 fix. Should be filed as a separate bug for future investigation.

### Patterns observed across stories

**Pattern A — Spec drafts from bug reports run small and clean.** All 8 specs landed at 124–137 lines (well under Rule 1's ≤ 250 cap). The bug report format ("description / reproduction / expected / actual / root cause / fix") maps almost 1:1 to AC contracts.

**Pattern B — Dual-flattener verbatim-copy invariant held.** Story 12.6 modified BOTH `MessageViewer.cls` and `VisualTrace.cls` `FlattenTurnsForBootstrap`. Reviewer verified executable code byte-identical (modulo pre-existing inline-comment drift). The Story 10.1 spec note about verbatim-copy maintenance proved load-bearing.

**Pattern C — Story 12.0 Carry-Forward (`node -c`) closed cleanly via Story 12.6.** The Rule 9 binding-deferrals system worked end-to-end: Story 10.13 deferred → bound to Story 12.1 + 12.6 in Story 12.0 Carry-Forward → Story 12.1 documented "binding does not apply" (no chat-panel.js modification) → Story 12.6 satisfied with verbatim `exit=0` capture → cr-12-6 marked CLOSED-by-12.6 in deferred-work.md. Full audit trail.

**Pattern D — Agent dispatch + reviewer dispatch pattern stable.** All 7 dev/reviewer pairs (12.1, 12.2, 12.3, 12.4, 12.5, 12.6, 12.7) used the spawn-on-demand pattern (unique names, `mode: bypassPermissions`, task-in-prompt, shutdown-before-respawn). Zero name collisions, zero self-scheduling races. The only deviation was Story 12.0 (lead-inline path for documentation), which was a deliberate Epic-1-retro-lesson-#4 choice — and the dev agent that DID get spawned for 12.0 (clarification path) caught the coverage drift.
