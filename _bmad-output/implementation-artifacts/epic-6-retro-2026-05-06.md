## Significant discoveries

**One — Manual-test bug shapes split into two distinct catch surfaces.**

- **Content / wire-format bugs** (Epic 5): visible to mock matrix + live tests if instrumented correctly (e.g., Bug 3 = matrix used hand-built tool array missing `additionalProperties`). Catchable structurally with the right fixture wiring.
- **Layout / rendering / operator-UX bugs** (Epic 6): NOT visible to any structural test. Require pixel-level rendering OR runtime DOM-state inspection (post-page-load combobox option count). The Rule 12 substitute evidence form (DOM paste) only catches the first class.

**Two — Class-of-bug stays consistent epic-over-epic.** Epic 5 catch surface = chat panel + operator storage path + runtime registry. Epic 6 catch surface = rendered form + operator state + runtime DOM materialization. Different stories, same shape: *bugs that only manifest when a real human drives the running system.* Project Lead has explicitly accepted the human-in-the-loop step (Epic 5 retro AI-1). The pattern is structurally repeatable across epics; plan capacity around it, don't try to engineer it away.

**Three — `Parameter PAGENAME` MPP5646 trap is reproducible.** Any future EnsPortal-subclass page in this codebase will hit it. Story 6.4 ate ~20 minutes of compile churn discovering the workaround. Worth codifying now so Epic 7+ doesn't relearn it.

**Four — Velocity itself is the metric.** 5 days, 6 epics complete, with working multi-provider LLM agent + operator-clickable config + multi-namespace install. Project Lead's surprise is the data telling us the velocity floor is higher than the mental model. Don't anchor Epic 8/9/10 capacity estimates on prior-project assumptions.
